Start Simple: The M×N Integration Problem

Before MCP, connecting an LLM to an external tool required custom integration code for every model-tool pair. Three models × ten tools = thirty custom integrations. Add a new tool: rewrite it for every model. Switch models: rewrite every integration.

MCP is to LLM tool use what HTTP is to web communication — a shared language that decouples producers (tool servers) from consumers (LLM hosts). Write a tool once as an MCP server; it works with any model that speaks MCP.

Core Concepts

Three-Layer Architecture

Host — the user-facing application (Claude Code, an IDE, a custom chatbot). Launches and manages MCP clients.

Client — lives inside the host; one client per server connection; translates between the host's needs and the MCP protocol.

Server — a lightweight process that exposes capabilities via MCP. Could be a filesystem bridge, a GitHub API wrapper, a database connector, a RAG pipeline — anything.

Three Capability Types

Tools — functions the LLM can invoke. Have a name, description, and JSON schema. The LLM reads the description and decides when to call the tool. Tool description quality determines tool call quality.

Resources — data the LLM can read, addressed by URI. File contents, database rows, live API responses. The LLM requests specific resources; the server fetches and returns them.

Prompts — reusable prompt templates exposed by the server. Surfaced to users as slash commands or quick actions (e.g. /review-code → structured code review prompt).

Key Questions Answered

Q: What problem does MCP solve that function calling doesn't?

A: Function calling defines how an LLM calls a function within one model's API. MCP defines how tools expose themselves in a model-agnostic way. Function calling is the LLM side; MCP is the tool side. With MCP, a tool built once works with any model that speaks MCP. Without it, the same tool requires a separate integration for every model.

Q: How do hosts, clients, and servers fit together?

A: The host is the user-facing application. It creates one MCP client per server it wants to connect to. Each client maintains a persistent connection to one MCP server running as a separate process. The LLM never talks to servers directly — all communication is mediated: LLM → host → client → server → result → client → host → LLM.

Q: What is the difference between a tool, a resource, and a prompt?

A: Tools are actions the LLM invokes to do things. Resources are data the LLM reads for context. Prompts are templates the host surfaces to users as shortcuts. A database server might expose execute_query as a tool, table schemas as resources, and a describe-schema prompt template.

Q: How does an MCP server expose capabilities to an LLM?

A: The server responds to tools/list with an array of tool definitions — each with a name, description, and JSON parameter schema. The host injects these into the LLM's context. The LLM reads the descriptions and decides when to call which tool. The description IS the API for the LLM: a vague description produces unreliable tool use.

Q: Why does standardisation matter for the agentic ecosystem?

A: Agents need many tools. Without a standard, building a capable agent requires custom integrations for every tool it uses. With MCP, tool builders write one server; agent builders write one client; both work together without coordination. The ecosystem grows in parallel. The analogy: USB-C vs proprietary connectors — standardisation enables composability at ecosystem scale.
