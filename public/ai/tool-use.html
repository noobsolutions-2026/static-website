Start Simple: What Is a Tool Call?

An LLM operating alone is bounded by text generation. Tool use removes that boundary. Give it a search tool and it can look things up. Give it a code executor and it can run programs. Give it an API client and it can act in the world.

The mechanism: the LLM emits a structured JSON object specifying a function name and arguments. The runtime executes it. The result is appended to the conversation. The LLM continues. The loop — reason, act, observe — is the same whether the tool is a calculator or a database.

Core Concepts

Tool Definition Anatomy

Every tool definition has three components:

  • Name — verb-noun form (search_web, read_file, execute_sql). The LLM parses the name — clear names improve selection accuracy.
  • Description — the most important field. Answers: what does this do, when should I use it, what does it return. Vague descriptions produce wrong tool calls.
  • Parameter schema — JSON Schema defining inputs. Include descriptions on every parameter, mark required fields, specify enums for finite value sets.

The Tool Call Lifecycle

The developer provides tool definitions. The LLM reads them and, when it needs external capability, emits a tool_use block. The runtime validates arguments, executes the function, and returns a tool_result. The LLM never executes code — it only proposes; the runtime decides whether and how to execute.

Parallel Tool Calls

When the LLM determines that multiple tools can be called without depending on each other's results, it emits multiple tool_use blocks in one response. The runtime executes them (potentially concurrently) and returns all results together. Use parallel calls when fetching independent data sources. Avoid when result A is needed as input to call B.

Key Questions Answered

Q: How does the LLM decide when and whether to use a tool?

A: Based entirely on the tool descriptions and the current context. There is no separate routing layer. The same model that generates text also decides to call tools — a capability learned from training on examples of appropriate tool use. Description quality is the primary control surface.

Q: What happens between the tool call and the result?

A: The LLM emits a tool_use block and stops. The runtime validates arguments against the schema, calls the actual function, handles errors, formats the result, and returns it as a tool_result block. The LLM then gets a new turn with the result in context. It has no visibility into what happened during execution — it only sees the formatted result.

Q: Why does description quality matter more than quantity?

A: With ten well-described tools, the LLM makes accurate selections and correct calls. With fifty vaguely-described tools, it struggles to pick the right one and often gets arguments wrong. Tool definitions also consume context window space — large toolsets eat into the capacity available for reasoning. A focused, well-documented toolkit outperforms a comprehensive but ambiguous one.

Q: How do parallel tool calls work?

A: The LLM emits multiple tool_use blocks in a single response when it determines calls are independent. The runtime executes them and returns all results together in the next turn. The model decides independence — this is part of its reasoning. Use parallel calls for fetching data from multiple independent sources; avoid when one result is input to the next call.

Q: What makes a tool reliable vs brittle in production?

A: Reliable tools are idempotent where possible, return structured results, and handle errors by returning useful error messages the LLM can act on. Brittle tools have side effects on every call, return unstructured text the LLM must parse, and throw raw exceptions that confuse the model. Designing tools for LLM consumption is different from designing them for humans.

Annotated References

  • Anthropic — Tool Use Documentation The reference implementation for tool use with Claude. The multi-turn examples showing tool_result handling are the most practically useful section.
  • Anthropic — Building Effective Agents Production insight: "the simplest working tool set" beats "the most comprehensive tool set." Fewer tools with clearer descriptions produce more reliable agent behaviour.
  • ReAct: Synergizing Reasoning and Acting Eight pages. Defines the Reason-Act-Observe pattern and shows it outperforms pure reasoning and pure acting on knowledge and decision tasks. The mental model behind most production agents.
  • Berkeley Function Calling Leaderboard Empirical benchmarks of model tool-calling accuracy. Useful for model selection when tool use is a primary workload.
