Start Simple: Why an LLM Needs a Library

Every LLM is a snapshot of text seen during training. Ask it about something written yesterday, a proprietary document, or a regulation that changed last month — and it can only hallucinate or admit ignorance. RAG is the simplest fix: retrieve relevant documents at query time, inject them into the prompt, let the LLM answer from that grounded context.

The core insight: an LLM that can read is more capable than one that only remembers. Knowledge lives outside the model; the model supplies the reasoning.

The Two Pipelines

Ingestion (offline, runs once per document collection)

Documents are split into chunks (the retrieval unit), each chunk is embedded into a high-dimensional vector, and the vector + chunk text is stored in a vector database.

flowchart LR Docs([Source Documents]) --> Split[Chunk\nSplit] Split --> Embed[Embed Each\nChunk] Embed --> Store[(Vector\nStore)]

Retrieval + Generation (online, per query)

The user's query is embedded using the same model, the top-K most similar chunk vectors are retrieved via cosine similarity, the chunks are injected into the prompt as context, and the LLM generates an answer grounded in that context.

Core Concepts

Chunking

The retrieval unit. Too small → loses context; too large → dilutes signal and fills the context window with noise. Common starting point: 512–1024 tokens with 10–20% overlap between adjacent chunks to prevent information loss at boundaries. Semantic chunking (splitting at paragraph boundaries) consistently outperforms fixed-size chunking.

Embeddings

A vector representation where semantically similar texts are positioned close together in high-dimensional space. The embedding model determines what "similar" means for your retrieval — a mismatch between the query's phrasing and the document's phrasing can cause correct content to be ranked poorly even if the meaning is identical.

Retrieval Quality

Retrieval quality is the bottleneck in almost every production RAG system. The generator (LLM) is rarely the problem. Common failure modes: relevant chunk not in the top-K; correct chunk retrieved but buried among irrelevant ones; retrieved chunks contradict each other; query phrasing doesn't match document phrasing despite identical meaning.

Key Questions Answered

Q: What problem does RAG solve that prompting alone cannot?

A: Knowledge cutoff and hallucination. Prompting can only work with what exists in the model's weights. RAG extends that with any document you can retrieve — proprietary data, recent events, domain-specific knowledge. The LLM contributes reasoning; the retrieval system contributes current, domain-specific knowledge.

Q: What happens at each step of the RAG pipeline?

A: Ingestion: documents → chunks → embeddings → vector store. Query: embed user query (same embedding model) → similarity search → retrieve top-K chunks → inject into prompt → LLM generates. The query and chunk embeddings must come from the same model — different embedding spaces are incompatible and will produce meaningless similarity scores.

Q: Why do retrieved documents sometimes hurt generation quality?

A: Three reasons. Irrelevant chunks add noise — the LLM may latch onto misleading content. Contradictory chunks confuse the model's synthesis. Too many chunks consume the context window, leaving less space for reasoning. Retrieval precision (not just recall) matters enormously. A single high-quality chunk often produces better answers than five mediocre ones.

Q: How do you choose chunk size and overlap?

A: Start with 512–1024 tokens and 10–20% overlap, then evaluate retrieval recall on a representative query set. Smaller chunks give more precise retrieval but less context per retrieved unit. Larger chunks give more context but are harder to match precisely. The right size depends on your documents: structured technical docs → larger; conversational transcripts or Q&A → smaller.

Q: When is RAG not enough — and what replaces it?

A: When the task requires reasoning over the entire corpus at once (RAG only retrieves fragments). When latency is critical (retrieval adds 100–500ms). When the knowledge is stable, well-defined, and comprehensive — fine-tuning bakes it into weights directly. When the task requires the model to have internalised a writing style, not just recall facts.

Annotated References

  • Lewis et al. — RAG for Knowledge-Intensive NLP Tasks The original paper. Read Sections 2–3 to understand the formulation. Key result: RAG outperforms parametric-only and retrieval-only baselines on open-domain QA.
  • Lilian Weng — Retrieval Augmented Generation Dense but comprehensive. Covers naive RAG, advanced RAG, and modular RAG with concrete failure modes. The best single reference for the full design space.
  • LlamaIndex — RAG Concepts Most practical entry point. Skips theory and shows how each component works with runnable examples. Start here before reading papers.
  • Anthropic — Contextual Retrieval Prepends document-level context to each chunk before embedding ("this chunk is from a contract describing X"). Significantly improves retrieval on documents where individual chunks lose meaning out of context.
  • Jerry Liu — Advanced RAG Techniques Illustrated overview of production improvements: HyDE, multi-query retrieval, re-ranking. Read after understanding naive RAG.
